## Executive findings

- **Verified:** A reusable typed workflow foundation exists. `packages/domain/src/workflow-contracts.ts` defines versioned workflow/task/artifact/approval/batch/error contracts; `WorkflowOperator`, `WorkflowStore`, `TaskRegistry`, `ArtifactRepository`, and `BatchCoordinator` in `packages/workflow-engine/src/` provide orchestration, event history, materialized state, attempts, cache decisions, locks, reconciliation, and batch execution.
- **Verified:** The foundation is not yet the sole execution authority. Dark Truth production still has a specialized `StoryWorkflowManifestStore` and many direct CLI paths; mathematics has both `math-workflow.v2` manifests and canonical workflow-engine adapters; story, image, and math batches retain separate manifests with canonical sidecars (`writeLegacyBatchSidecar` in `packages/workflow-engine/src/batch-adapters.ts`).
- **Verified:** The canonical Dark Truth registry is a task graph without production execution bindings: `createOperator` in `apps/cli/src/workflow-commands.ts` calls `createDarkTruthTaskRegistrations` without implementations, and `WorkflowOperator.runTask` blocks when `implementation.execute` is absent. Mathematics is materially further migrated: `createCanonicalMathOperator` in `apps/cli/src/math-workflow-runtime.ts` binds implementations returned by `createMathProductionTaskImplementations`, but `packages/math-education/src/orchestration/canonical-task-adapters.ts` stops at `math.publish-dry-run`; `math.publish-approval` and `math.publish` remain unbound.
- **Verified:** Current authoritative workflow state is local filesystem state scoped to a production unit. `WorkflowStore` writes `state/workflow/<workflow-id>/events.jsonl`, `state.json`, approvals, overrides, locks, run attempts, and cache decisions beneath `unitRoot`; specialized story and math manifests use different directories and schemas.
- **Verified:** The only relational persistence is `SQLitePersistence` in `packages/persistence/src/index.ts`, whose migration creates only an `episodes` table containing serialized episode manifests. `apps/cli/src/index.ts:885-886` opens and migrates it, but production CLI code does not call its manifest save/load methods; focused search found those methods used only in `packages/persistence/src/index.integration.test.ts`.
- **Verified:** There is no general durable queue dependency or multi-node job store in package manifests. Concurrency is implemented with in-process loops, promises, semaphores, and JSON checkpoints (`BatchCoordinator`, `runMathBatch`, `MathPrivateBatchScheduler`); OpenAI provider batches and SSH/Docker render jobs are external jobs wrapped by local files.
- **Verified:** Existing publication code has strong approval binding and partial-progress reuse, but it cannot guarantee exactly-once YouTube publication across the crash window after `videos.insert` succeeds and before the returned video ID is durably recorded.
- **Recommended:** Treat the current code as evidence-rich adapters, not as production API persistence. Make a relational application/workflow database authoritative, retain an append-only workflow event history plus current-state tables, execute long work from durable claimed jobs, and keep filesystem JSON as a transitional import/materialized compatibility projection.

## Canonical workflow behavior and gaps

### State machine, attempts, cache, and recovery

- **Verified:** Canonical task statuses are `pending`, `ready`, `blocked`, `running`, `succeeded`, `failed`, `interrupted`, `skipped`, `invalidated`, and `awaiting-approval`; transitions fail closed through `allowedTransitions` and `WorkflowStore.assertTransition` (`packages/domain/src/workflow-contracts.ts`, `packages/workflow-engine/src/workflow-store.ts:197-249`).
- **Verified:** `WorkflowOperator.runTask` derives a fingerprint, records a cache decision, invalidates stale successes and descendants, checks graph readiness, acquires a file lock, writes a running attempt, invokes the registered implementation, validates output lineage, records telemetry, and completes the attempt (`packages/workflow-engine/src/workflow-operator.ts:327-583`).
- **Verified:** Cache hits require matching task/dependency fingerprints and verified output manifests; canonical attempt history is intentionally immutable and `planCachePrune` refuses to delete it (`packages/workflow-engine/src/cache.ts`, `WorkflowOperator.planCachePrune`).
- **Verified:** `resume()` recovers stale records, selects the first interrupted task, transitions it to pending, and executes a new attempt. `retryFailed()` similarly selects the first failed task. Neither API accepts a target attempt/task, which is ambiguous if multiple tasks are interrupted/failed (`packages/workflow-engine/src/workflow-operator.ts:587-621`).
- **Verified:** The task definition fields `policies.retryLimit` and `policies.timeoutMs` are not read by `WorkflowOperator`; focused search finds their runtime use only in `BatchCoordinator`. Canonical non-batch retries are therefore explicit and unbounded by task policy, and task execution has no workflow-engine timeout enforcement.
- **Verified:** `WorkflowStore.heartbeatLock` exists, but `WorkflowOperator.runTask` never calls it. Its default stale threshold is 15 minutes, so an active long render/provider task can be classified stale and its lock removed based on elapsed heartbeat time even while the process remains alive (`workflow-store.ts:343-360,1086-1203`; `workflow-operator.ts:376-583`).
- **Verified:** The crash window between artifact promotion and attempt completion is intentionally reconcilable when validated artifact manifests are supplied: `WorkflowStore.reconcile` can complete a matching running attempt or invalidate a materialized success with missing outputs. `workflow-store.unit.test.ts:499` characterizes this behavior.
- **Verified:** Filesystem event append and projection update are separate operations. A crash after appending remains recoverable by `rebuildState`; `workflow-store.unit.test.ts:154` tests corrupt/interrupted projection rebuild.
- **Verified:** Cross-process event transitions do not have compare-and-swap or a workflow-instance append lock. `appendEventAndRebuild` reads current events, appends a JSONL event, then rebuilds; two processes can derive the same `from` state and append conflicting events. Task execution locks reduce but do not eliminate this for approvals, overrides, invalidations, and other transitions.
- **Verified:** Approval/override containers are read-modify-replace JSON without an enclosing cross-process lock (`ensureOperatorRecord`), so concurrent writers can lose a record even if event appends succeed.
- **Recommended:** Before API reuse, enforce task timeout/retry policy, heartbeat or lease renewal, explicit target IDs for resume/retry, workflow-instance optimistic concurrency, and atomic state/event/job updates in a transactional store.

### Batch and cancellation behavior

- **Verified:** `BatchCoordinator` creates deterministic item IDs from task/unit/locale/variant/fingerprint and a deterministic batch ID from profile/provider/model/operation/item IDs; it resumes persisted successful/permanent/cancelled items and retries other items (`packages/workflow-engine/src/batch.ts`).
- **Verified:** Canonical batch concurrency and manifest mutation serialization are process-local. `updateTail` prevents competing writes only within one coordinator instance; `BatchStore.write` has no lease, revision check, or cross-process lock.
- **Verified:** `BatchCoordinator.cancel` marks pending, running, and retryable items cancelled in the manifest, but it does not abort an already executing `TaskImplementation`; the supplied `AbortSignal` is checked before each item, not passed into the task execution context. A running task may still finish and overwrite cancelled state.
- **Verified:** Story and image provider batches implement prepare, submit, refresh, download/import, retry lineage, and provider cancellation. Their provider batch IDs and item custom IDs support resume/reconciliation (`story-localization-batch-service.ts`, `image-batch-service.ts`).
- **Verified:** Both story and image submission perform external operations before saving the provider IDs locally: upload input, create provider batch, then update the local manifest. A crash after provider acceptance can orphan a paid batch and a subsequent submit can create another remote batch because the manifest still says `prepared`.
- **Verified:** Story/image import is protected by `withFileLock`, but this lock has a fixed age and no heartbeat; after five minutes another process can remove it even if a long import remains active (`packages/story-localization/src/story-localization-batch-storage.ts:244-302`).
- **Verified:** `runMathBatch` is sequential, checkpoints after each item, applies bounded retry, and skips previously succeeded/permanent/blocked items. `MathPrivateBatchScheduler` adds process-local preparation serialization, a render semaphore, paid-speech rate spacing, scene JSON queue state, resume/retry routing, and cancellation of recorded remote job IDs (`packages/math-education/src/orchestration/batch.ts`; `apps/cli/src/math-private-batch-scheduler.ts`).
- **Verified:** The mathematics render “queue” is a JSON file plus in-process scheduler, not a consumer queue. Store updates are serialized only within one `MathRenderQueueStore` instance.
- **Recommended:** Model cancellation as a durable request state (`cancel_requested`) observed by workers; propagate an `AbortSignal` to providers/renderers; record whether each side effect is cancellable; and move unclaimed work to a dead-letter state after bounded attempts rather than marking in-flight work cancelled optimistically.

## External side effects and duplicate-publication analysis

### What exists

- **Verified:** `publishYoutubeMedia` requires a current `PublishApproval` bound to content identity, channel/account, exact artifact hashes/revisions, metadata hash/revision, playlist policy, and request hash (`packages/youtube-upload/src/publish-approval.ts`, `generic-media-publish.ts`).
- **Verified:** It validates prior reports, binds operation evidence to request fingerprint/video ID, rejects stale or non-authority-loaded reports, reuses complete reports, and resumes only incomplete mutations. Tests cover approval gating, stale/cross-video report rejection, partial playlist retry, checkpoint resume, and contained hash-verified report loading (`generic-media-publish.unit.test.ts:187-466`).
- **Verified:** `executeYoutubeMutationSequence` retries retryable YouTube errors with backoff, records provider request IDs when headers provide them, validates the authenticated channel, inserts the video, sets thumbnail, inserts playlists, and verifies the video (`youtube-mutation-seam.ts`).
- **Verified:** Generic checkpoints are callbacks invoked only after the YouTube request returns successfully. The legacy `uploadYoutubeEpisode` callback records telemetry/request IDs but does not persist intermediate progress; it overwrites the initially planned report only after the full sequence (`packages/youtube-upload/src/index.ts:1498-1859`).

### Exact failure

- **Verified:** There is no transaction spanning YouTube and local storage, no publication-intent table, no outbox/effect receipt, and no provider idempotency key passed to `videos.insert`.
- **Inferred:** If YouTube accepts the upload and the process dies before `videos.insert` returns or before its video ID checkpoint commits, local state remains “no video.” An automatic retry can call `videos.insert` again and publish a duplicate.
- **Inferred:** The same, smaller ambiguity exists for playlist insertion; a retry after an unrecorded success can add the same video to the same playlist again.
- **Recommended:** Treat an unknown result from any irreversible mutation as `outcome_uncertain`, never as ordinary retryable failure.

### Precise target design

1. **Recommended:** In one database transaction create a `publication_intent` with a unique constraint on `(workspace_id, target_channel_id, content_revision_id, variant, locale)` and store the API `Idempotency-Key`, canonical request fingerprint, approval ID/hash, and status `prepared`.
2. **Recommended:** Create one `external_effect` per mutation (`youtube.video.insert`, thumbnail, each playlist, verification) with a deterministic effect ID and unique `(publication_intent_id, operation, target_key)`. Enqueue the publication job through a transactional outbox in the same transaction.
3. **Recommended:** A worker claims the intent using a renewable lease and revision check. Only the lease owner may mutate or checkpoint. The workflow publication step remains `running/outcome_uncertain` until effects reconcile.
4. **Recommended:** Use an explicit resumable-upload adapter rather than the current opaque `googleapis` convenience call. Persist the resumable session URI and provider request identifiers before sending video bytes where the provider protocol permits it.
5. **Recommended:** Upload initially as `private` and attach a unique exact recovery marker (prefer a temporary private tag) derived from the publication intent. Persist the returned YouTube video ID as an effect receipt immediately, before thumbnail/playlist/scheduling work.
6. **Recommended:** On restart with no receipt, do not start another upload. First query the saved resumable session. If still inconclusive, enumerate the authenticated channel’s recent uploads and fetch video snippets/status, matching the exact temporary recovery marker and channel. One match becomes the receipt; zero matches after a conservative provider-defined uncertainty window permits a new upload session; multiple matches dead-letter and require operator resolution.
7. **Recommended:** After the receipt is durable, run idempotent downstream effects. Before `playlistItems.insert`, list existing playlist items for the target video or maintain and reconcile exact playlist item IDs. Persist each successful receipt before proceeding.
8. **Recommended:** Only after video receipt, thumbnail, playlists, and verification are durable should a final metadata update remove the recovery marker and apply the approved schedule/privacy. Mark the publication and workflow step succeeded in one local transaction.
9. **Recommended:** Never allow `force` to bypass the unique intent. A privileged operator may create a new content revision/publication intent with an audited reason.

- **Unresolved:** Confirm YouTube resumable-session status/recovery guarantees and whether an exact temporary tag is reliably returned through `videos.list` for the authenticated channel. If either is insufficient, the pilot must fail closed on uncertain video insertion and require manual channel reconciliation; no architecture can claim exactly once without a provider-observable recovery identity.

## Target persistence model

### Options

| Option                                    | Assessment                                                                                                                                                                                                                                                                                           |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing JSON workflow logs authoritative | **Verified:** They provide useful versioned evidence, local atomic writes, rebuild, hashes, and compatibility. **Recommended:** Reject as API authority because cross-process CAS, tenant queries, leases, referential integrity, backup/restore coordination, and atomic outbox updates are absent. |
| Relational current-state tables only      | **Recommended:** Reliable and simplest for jobs, filtering, permissions, leases, optimistic concurrency, and transactions. **Inferred:** Without immutable history it would weaken current forensic/reconciliation value.                                                                            |
| Full event sourcing with projections      | **Recommended:** Do not adopt for v1. Current event concepts are useful, but full event-sourced domain reconstruction adds migration and operational cost while specialized stores still diverge.                                                                                                    |
| Durable-execution framework as authority  | **Unresolved:** No such framework or dependency exists. It may later help long timers and fan-out, but cannot replace domain/application records, approvals, publications, assets, or tenant authorization.                                                                                          |
| Transitional hybrid                       | **Recommended:** Use relational state plus append-only events as the target, with JSON import/export adapters during migration. This is hybrid storage, not dual authority.                                                                                                                          |

### Smallest reliable schema boundary

- **Recommended:** Use relational tables for `workflow_definitions`, `workflow_runs`, `workflow_steps`, `step_attempts`, `jobs`, `job_leases`, `approvals`, `assets`, `asset_lineage`, `validation_results`, `publication_intents`, `external_effects`, `outbox_events`, and `dead_letters`.
- **Recommended:** Put `workspace_id` on every tenant-owned row and include it in unique and foreign-key relationships. Give mutable aggregate rows a monotonically increasing `revision`; require `WHERE id=? AND revision=?` updates.
- **Recommended:** Keep `workflow_events` append-only with correlation/causation IDs and a per-run sequence unique constraint. Use it for history/rebuild/diagnostics, but make transactional current-state rows the command/read authority.
- **Recommended:** Claim jobs with database leases (`claimed_by`, `lease_expires_at`, `heartbeat_at`, `attempt_count`) and a single transaction/locking primitive appropriate to the selected database. Expired leases return work to runnable only when the step’s effect policy permits retry.
- **Recommended:** Make step attempt records immutable after terminalization; retries create new attempts. Store normalized error code, retry class, provider request ID, costs, input fingerprint, output asset IDs, and timestamps.
- **Recommended:** Make queue state and workflow state change in the same transaction. The outbox publishes webhook/notification events after commit; consumers deduplicate by event ID.
- **Recommended:** PostgreSQL or an equivalent multi-writer relational database is the production target. SQLite may remain a local/offline compatibility mode but should not back horizontally scaled API/workers.

### Migration without split authority

- **Recommended:** Phase 1 reads existing JSON and creates characterization tests; do not dual-write yet.
- **Recommended:** Phase 2 adds repository ports and imports/indexes JSON into relational records with source path, source schema version, and source hash. Imported historical runs are immutable.
- **Recommended:** Phase 3 launches new API runs with the database authoritative and materializes filesystem JSON only through a compatibility projection/outbox consumer. A projection failure does not roll back canonical state and is visible as a repairable job.
- **Recommended:** Phase 4 migrates CLI commands to the same application use cases. For a given workflow instance, store an explicit authority marker (`filesystem-legacy` or `database-v1`) and reject writes through the wrong adapter.
- **Recommended:** Phase 5 retires specialized writable stores only after story/image/math characterization and resume tests pass. Retain read-only importers for old episodes.

## Assets and filesystem bridge

- **Verified:** Current asset contracts already contain most migration primitives: logical ref, relative path, SHA-256, size, media type, producing task/version/attempt, validation identity/version, dependency fingerprints, and creation time (`artifactManifestSchema`).
- **Verified:** `ArtifactRepository` rejects ambiguous different-content candidates and path/symlink escapes, and canonical paths differ by content profile without exposing those differences in the logical `ArtifactRef`.
- **Recommended:** Preserve this logical contract behind an `AssetRepository` port. Public resources expose opaque asset IDs, never local paths, relative paths, or storage provider keys.
- **Recommended:** For the first internal pilot, support a local-filesystem storage driver only on a single shared volume while the relational database owns asset metadata. Require contained paths and checksum verification on every promotion/read.

- **Recommended:** Upload to a temporary quarantined key; validate checksum/MIME/container; copy or promote to an immutable final key; then commit the asset row. Delete temporary objects via retention jobs. Never overwrite an immutable final object.
- **Recommended:** Serve large videos through short-lived object-storage/CDN URLs with authorization checked before signing; do not proxy them through the API process by default.
- **Recommended:** Model retention state (`temporary`, `retained`, `legal_hold`, `deletion_pending`, `deleted`) and make cleanup idempotent. Cross-tenant copy/reuse must create a new authorized logical asset binding even when physical content is hash-deduplicated.
