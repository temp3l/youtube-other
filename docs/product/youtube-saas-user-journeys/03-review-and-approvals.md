# Review and approvals

## US-002 — Review Queue
**Persona:** reviewer. **User story:** As a reviewer, I want a tenant-scoped actionable queue so that I only decide current challenges. **Entry conditions:** reviewer role. **Primary journey:** 1. Open queue. 2. Filter role/expiry/profile. 3. Inspect tenant, episode/revision, artifact hash, challenge revision and validation summary. 4. Approve/reject/request changes. **Alternate journeys:** expired/consumed challenge is historical, not actionable. **Failure / recovery journeys:** stale hash rejects decision and returns current review requirement. **API/domain expectations:** tenant-wide actionable challenge projection, exact subject/hash/role/expiry. **Frontend expectations:** no fabricated queue; clear expiry/staleness. **Security / tenant-isolation requirements:** `approval.decide` plus challenge scope. **Idempotency / concurrency requirements:** one decision consumes exact challenge; ETag/idempotency prevents double decision. **Audit requirements:** decision/challenge/hash. **Acceptance criteria:** Given an expired challenge, when queue loads, then it cannot be approved. **Open questions:** reviewer assignment policy. **Existing implementation evidence:** exact challenge/decision UI exists but web explicitly lacks tenant-wide queue; `apps/api/src/contract.ts`, `apps/web/src/saas-runtime.ts`. **PARTIAL.**

## US-026 — Submit for Review
**Persona:** producer. **User story:** As a producer, I want to submit an exact revision/artifact set so that review scope is unambiguous. **Entry conditions:** validations satisfy submission gate. **Primary journey:** 1. Select revision and required artifact hashes. 2. Review validation/gate summary. 3. Select reviewer role/expiry. 4. Submit challenge. **Alternate journeys:** approval mode automatic only when policy explicitly permits. **Failure / recovery journeys:** invalid/stale evidence blocks submission and links correction. **API/domain expectations:** challenge binds subject revision, artifact hash, role, expiry and policy version. **Frontend expectations:** explicit immutable scope confirmation. **Security / tenant-isolation requirements:** producer can submit; reviewer scope is least privilege. **Idempotency / concurrency requirements:** submission key per revision/scope; duplicate returns same active challenge. **Audit requirements:** submitter/scope/expiry. **Acceptance criteria:** Given changed artifact hash, when submit is attempted with old set, then submission is refused. **Open questions:** multi-reviewer quorum rules. **Existing implementation evidence:** approval challenge contracts/persistence exist; dedicated producer submit journey is incomplete. **PARTIAL.**

## US-027 — Review Decision
**Persona:** reviewer. **User story:** As a reviewer, I want to approve, reject, or request changes against exact evidence so that the decision is trustworthy. **Entry conditions:** active, authorized challenge. **Primary journey:** 1. Inspect artifacts/validation. 2. Compare displayed revision/hash/challenge. 3. Choose decision and rationale. 4. Receive immutable decision/result state. **Alternate journeys:** reviewer withdraws from unstarted challenge if assignment policy allows. **Failure / recovery journeys:** consumed/expired/stale challenge rejects safely and directs new review. **API/domain expectations:** decision consumes challenge and records exact bindings. **Frontend expectations:** decision controls unavailable unless evidence current. **Security / tenant-isolation requirements:** reviewer role and tenant scope. **Idempotency / concurrency requirements:** same decision key is replay-safe; competing decision has one winner. **Audit requirements:** actor, rationale, decision, hash/revision/time. **Acceptance criteria:** Given two reviewers submit simultaneously, when one succeeds, then the other receives a non-destructive consumed/stale response. **Open questions:** rejection rationale minimum. **Existing implementation evidence:** `recordApproval`, challenge binding and BFF approve/reject flows in `apps/api/src/contract.ts`, `apps/web/src/saas-runtime.ts`; tests include approval persistence. **EXISTS.**

## US-028 — Stale Review Protection
**Persona:** producer/reviewer. **User story:** As a user, I want review validity evaluated after change so that approvals never cover altered evidence. **Entry conditions:** submitted or decided challenge. **Primary journey:** 1. Change artifact/config/revision. 2. Re-evaluate binding. 3. Mark valid/stale with reason. 4. Require re-review when policy says. **Alternate journeys:** unrelated artifact change leaves narrowly-scoped approval valid. **Failure / recovery journeys:** unable-to-evaluate binding blocks downstream gate. **API/domain expectations:** validity evaluator compares exact revision, hashes and configuration policy; retain original decision. **Frontend expectations:** “stale” never looks approved; explains impact. **Security / tenant-isolation requirements:** no unscoped decision disclosure. **Idempotency / concurrency requirements:** validity calculated against immutable data. **Audit requirements:** invalidation trigger/reason. **Acceptance criteria:** Given approved render then regenerated audio, when publish gate runs, then approval is stale if audio is in approved set. **Open questions:** configuration fields that invalidate each review type. **Existing implementation evidence:** challenge hash/revision/expiry binding and server rejection exist; cross-artifact invalidation matrix absent. **PARTIAL.**

## US-029 — Approval History
**Persona:** reviewer/admin. **User story:** As an authorized user, I want review history so that I can understand decisions without overwriting them. **Entry conditions:** episode/revision access. **Primary journey:** 1. Open history. 2. Filter revision/artifact/role/time. 3. Inspect submitted, decision, expiry, revocation and stale events. 4. Navigate evidence. **Alternate journeys:** history redacts rationale based on role. **Failure / recovery journeys:** historical missing artifact shows retained hash/provenance. **API/domain expectations:** append-only approval/event projection distinct from active challenge list. **Frontend expectations:** chronological history and current-validity label. **Security / tenant-isolation requirements:** authorized audit/read role. **Idempotency / concurrency requirements:** immutable history. **Audit requirements:** history is itself sourced from audit/approval records. **Acceptance criteria:** Given revoked approval, when history opens, then original decision and revocation appear without presenting it as current. **Open questions:** reviewer-comment visibility. **Existing implementation evidence:** approval record/revoke operations/persistence exist; broad history/list UI/read model is incomplete. **PARTIAL.**
