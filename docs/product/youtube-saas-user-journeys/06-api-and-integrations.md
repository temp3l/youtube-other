# API and integrations

## US-021 — Cost / Usage Preflight
**Persona:** producer. **User story:** As a producer, I want an estimated usage preflight so that I can decide before expensive work. **Entry conditions:** proposed workflow scope. **Primary journey:** 1. Select work. 2. View estimated LLM/image/TTS/localization/render use, quota and cache/reuse effects. 3. Confirm/admit. **Alternate journeys:** provider-free estimate is zero/exempt. **Failure / recovery journeys:** unknown price/capability blocks or requires policy confirmation. **API/domain expectations:** estimate is distinct from actual ledger and labels confidence/basis. **Frontend expectations:** estimate, reuse assumptions, no billing promise. **Security / tenant-isolation requirements:** tenant entitlements only. **Idempotency / concurrency requirements:** admission rechecks quota. **Audit requirements:** optional accepted estimate snapshot. **Acceptance criteria:** Given cached artifact reuse, when preflight runs, then estimate identifies avoided work. **Open questions:** unit/currency exposure. **Existing implementation evidence:** workflow admission/budget tiers and provider-free mode exist; complete preflight estimator absent. **PARTIAL.**

## US-022 — Actual Usage
**Persona:** admin. **User story:** As an admin, I want actual consumption by episode/run/profile/provider/time so that I can operate independently of provider invoices. **Entry conditions:** usage-read grant. **Primary journey:** 1. Choose filters. 2. Inspect append-only measures/attribution. 3. Export or drill into run. **Alternate journeys:** provider identity unavailable is labelled. **Failure / recovery journeys:** delayed reconciliation shows freshness. **API/domain expectations:** product usage ledger, not assumed billing API. **Frontend expectations:** totals/units/basis and pagination. **Security / tenant-isolation requirements:** tenant-scoped financial access. **Idempotency / concurrency requirements:** reconciliation dedupe. **Audit requirements:** usage adjustments. **Acceptance criteria:** Given two runs, when filtered by episode, then only attributable consumption is summed. **Open questions:** cost allocation rules. **Existing implementation evidence:** `PostgresUsageAuditRepository`, API contracts and BFF usage view. **PARTIAL.**

## US-023 — Quotas / Budgets
**Persona:** admin/producer. **User story:** As a user, I want quota visibility and admission rules so that limits are predictable. **Entry conditions:** configured entitlement/quota. **Primary journey:** 1. View remaining/warnings/hard limit. 2. Preflight. 3. Start or receive refusal. **Alternate journeys:** soft limit permits authorized override. **Failure / recovery journeys:** quota race rejects before provider effect. **API/domain expectations:** tenant quotas, policy, current window and admission result. **Frontend expectations:** clear warning/hard-block distinction. **Security / tenant-isolation requirements:** billing data privileged. **Idempotency / concurrency requirements:** atomic admission reservation. **Audit requirements:** limit/override/rejection. **Acceptance criteria:** Given hard limit exhausted, when workflow starts, then no job/effect is created. **Open questions:** reservation expiration. **Existing implementation evidence:** quota endpoint/admission schemas in `apps/api/src/contract.ts`; operational configuration is pilot-limited. **PARTIAL.**

## US-024 — Provider Health
**Persona:** admin/producer. **User story:** As a user, I want safe provider capability health so that I can choose a viable path. **Entry conditions:** provider-backed or provider-free profile. **Primary journey:** 1. View capability status: available, unavailable, unconfigured, degraded, unsupported, fallback available. 2. Run authorized test. 3. Choose fallback or defer. **Alternate journeys:** provider-free displays intentional mode. **Failure / recovery journeys:** degradation blocks only dependent actions. **API/domain expectations:** capability health, safe identity/test result, no secret. **Frontend expectations:** state/recommendation, never credential values. **Security / tenant-isolation requirements:** configuration status role-scoped. **Idempotency / concurrency requirements:** health timestamps/version. **Audit requirements:** tests/config changes. **Acceptance criteria:** Given unconfigured TTS, when voice preflight opens, then it states unavailable and no credential field is exposed. **Open questions:** health polling cadence. **Existing implementation evidence:** safe integration-disabled UI and speech status; complete provider health registry absent. **PARTIAL.**

## US-041 — API Credentials
**Persona:** admin. **User story:** As an admin, I want scoped service credentials so that external clients use least privilege. **Entry conditions:** credential-admin authorization. **Primary journey:** 1. Create/name/scope credential. 2. Display secret once only where policy permits. 3. Rotate/revoke and inspect last-use metadata. **Alternate journeys:** service principal backed by external identity. **Failure / recovery journeys:** revoked/expired key fails safely. **API/domain expectations:** hashed secret, scopes, lifecycle and principal binding. **Frontend expectations:** never redisplay secret; copy-confirmation. **Security / tenant-isolation requirements:** tenant-bound scopes and secret handling. **Idempotency / concurrency requirements:** rotation creates a new version; revoke ETag. **Audit requirements:** create/rotate/revoke/use metadata. **Acceptance criteria:** Given revoked credential, when request repeats, then authorization fails and audit identifies key ID only. **Open questions:** maximum active rotation overlap. **Existing implementation evidence:** `PilotApiKeyService`, admin command and persistence exist; SaaS credential management is deliberately absent. **PARTIAL.**

## US-042 — API Workflow Client
**Persona:** developer/API consumer. **User story:** As a developer, I want to create content and run production programmatically so that my system integrates natively. **Entry conditions:** scoped credential. **Primary journey:** 1. Create project/episode brief. 2. Start pinned workflow. 3. Receive run ID. 4. Poll or receive event. 5. coordinate review. 6. retrieve approved results. **Alternate journeys:** provider-free profile for integration tests. **Failure / recovery journeys:** typed problem/retry guidance. **API/domain expectations:** stable contracts for project/episode/run/status/assets/approvals. **Frontend expectations:** API explorer links from developer settings. **Security / tenant-isolation requirements:** scopes/membership per operation. **Idempotency / concurrency requirements:** standard idempotency keys and preconditions. **Audit requirements:** service principal/correlation. **Acceptance criteria:** Given valid scope, when client starts workflow, then it receives a tenant-scoped run ID and can retrieve safe state. **Open questions:** external client review delegation. **Existing implementation evidence:** OpenAPI SDK core operations in `apps/api/src/contract.ts` and `packages/api-sdk/src/v1-contract.ts`; full external support is pilot-limited. **PARTIAL.**

## US-043 — API Idempotency
**Persona:** developer. **User story:** As a developer, I want retry-safe requests so that timeouts do not duplicate content, decisions or publication. **Entry conditions:** mutation endpoint. **Primary journey:** 1. Send idempotency key/request. 2. Timeout/retry same key. 3. Receive original result or conflict if payload differs. **Alternate journeys:** optimistic concurrency conflict triggers refresh. **Failure / recovery journeys:** ambiguous irreversible effect enters reconciliation. **API/domain expectations:** durable key per tenant/principal/operation, payload digest/result and expiry. **Frontend expectations:** client retries only safe documented operations. **Security / tenant-isolation requirements:** keys cannot replay across tenant/principal. **Idempotency / concurrency requirements:** explicitly covers create, workflow start, approval and publish. **Audit requirements:** original/replay linkage. **Acceptance criteria:** Given repeated workflow start with same key, when retried, then exactly one run exists. **Open questions:** retention duration. **Existing implementation evidence:** `If-Match` and some command idempotency exist; Task 09 records project/episode create replay as process-local, not durable. **PARTIAL.**

## US-044 — Webhooks
**Persona:** developer. **User story:** As a developer, I want event subscriptions so that my system reacts to workflow/review/publication state. **Entry conditions:** integration-admin scope. **Primary journey:** 1. Register endpoint/event filters. 2. Verify/test. 3. Receive workflow/review/readiness/publication events. 4. acknowledge/retry as needed. **Alternate journeys:** poll API instead. **Failure / recovery journeys:** endpoint failure retries/backoff and records history. **API/domain expectations:** durable outbox/event catalogue and endpoint resource. **Frontend expectations:** safe endpoint/filter management. **Security / tenant-isolation requirements:** endpoint is tenant scoped/HTTPS. **Idempotency / concurrency requirements:** event ID enables consumer dedupe. **Audit requirements:** subscription changes/delivery. **Acceptance criteria:** Given workflow completion, when subscribed, then a uniquely identified tenant event is scheduled. **Open questions:** supported event versioning. **Existing implementation evidence:** `PostgresWebhookRepository`, webhook worker/provision command; customer API/UI surface is disabled. **PARTIAL.**

## US-045 — Webhook Security
**Persona:** developer. **User story:** As a developer, I want verifiable deliveries so that endpoint events are safe to consume. **Entry conditions:** endpoint/secret configured. **Primary journey:** 1. Store signing secret server-side. 2. Receive event ID/timestamp/signature. 3. verify within tolerance/dedupe. 4. Rotate secret with overlap policy. **Alternate journeys:** test delivery. **Failure / recovery journeys:** invalid/replayed request is rejected by consumer; delivery state records reason. **API/domain expectations:** HMAC/signature version, secret ref, IDs/timestamps and replay semantics. **Frontend expectations:** describe verification without revealing secret. **Security / tenant-isolation requirements:** tenant-specific secret and SSRF-safe endpoint validation. **Idempotency / concurrency requirements:** replay-safe event ID. **Audit requirements:** secret rotation/verification test. **Acceptance criteria:** Given replayed event ID, when consumer processes it, then duplicate effect is prevented. **Open questions:** signing algorithm/overlap interval. **Existing implementation evidence:** signing-secret resolver, HTTPS/DNS safeguards and delivery tests in `apps/api/src/{webhook-process,node-webhook-delivery}.ts`. **PARTIAL.**

## US-046 — Webhook Delivery History
**Persona:** developer. **User story:** As a developer, I want delivery history so that I can diagnose integration failures. **Entry conditions:** subscription access. **Primary journey:** 1. Filter endpoint/event. 2. Inspect attempt, safe response status, retry and next attempt. 3. Correlate event/payload identity. **Alternate journeys:** resend eligible event. **Failure / recovery journeys:** terminal failure shows safe remediation. **API/domain expectations:** durable attempt projection and redacted payload metadata. **Frontend expectations:** no secret headers/full sensitive body. **Security / tenant-isolation requirements:** endpoint owner only. **Idempotency / concurrency requirements:** resend is distinct attempt for same event ID. **Audit requirements:** resend/action. **Acceptance criteria:** Given 5xx delivery, when history opens, then status/retry/next attempt are visible. **Open questions:** redaction/export policy. **Existing implementation evidence:** durable repository/worker supports attempts; customer read UI/API not established. **PARTIAL.**

## US-047 — Developer/API Explorer
**Persona:** developer. **User story:** As a developer, I want canonical examples/docs so that I can integrate without reverse-engineering UI. **Entry conditions:** developer access. **Primary journey:** 1. Open generated contract. 2. Authenticate using scoped credential. 3. Follow create→run→status→review→result example. **Alternate journeys:** provider-free sandbox example. **Failure / recovery journeys:** version mismatch links migration guide. **API/domain expectations:** generated OpenAPI/types are source, examples reference operation IDs. **Frontend expectations:** explorer never duplicates divergent manual contract. **Security / tenant-isolation requirements:** examples use placeholders. **Idempotency / concurrency requirements:** examples show keys/ETags. **Audit requirements:** N/A. **Acceptance criteria:** Given a contract change, when explorer renders, then it references regenerated authoritative schema. **Open questions:** public vs tenant-authenticated docs. **Existing implementation evidence:** `apps/api/src/contract.ts` produces OpenAPI and `packages/api-sdk` type-safe client; dedicated explorer remains absent. **PARTIAL.**
