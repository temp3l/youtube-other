# Templates, retention, and onboarding

## US-048 — Clone Episode
**Persona:** producer. **User story:** As a producer, I want to clone episode content safely so that I can reuse a starting point without copying runtime identity. **Entry conditions:** readable source/target project. **Primary journey:** 1. Choose source revision. 2. Select reusable content/config. 3. Create new episode/brief. 4. Confirm new identity and blank runtime/review/publication state. **Alternate journeys:** clone as localized derivative only through US-012. **Failure / recovery journeys:** prohibited shared/restricted asset is omitted with reason. **API/domain expectations:** clone command with explicit copy policy. **Frontend expectations:** checklist distinguishing copied content from reset identity. **Security / tenant-isolation requirements:** source/target authorization and asset rights. **Idempotency / concurrency requirements:** clone key prevents duplicate new episodes. **Audit requirements:** source/target IDs. **Acceptance criteria:** Given approved source, when cloned, then new episode has no workflow run, approval or publication identity. **Open questions:** cross-tenant cloning policy. **Existing implementation evidence:** versioned episode create/revise exists; clone semantics absent. **MISSING.**

## US-049 — Production Template
**Persona:** producer/admin. **User story:** As a user, I want reusable production templates separate from episode content so that defaults are governed. **Entry conditions:** template permission. **Primary journey:** 1. Create/version template. 2. Set allowed config/metadata defaults. 3. Apply to new episode. 4. Resolve/pin configuration. **Alternate journeys:** fork template. **Failure / recovery journeys:** invalid template blocks activation, not existing episodes. **API/domain expectations:** template resource distinct from profile and episode revision. **Frontend expectations:** shows inherited fields/source. **Security / tenant-isolation requirements:** template sharing policy. **Idempotency / concurrency requirements:** version/ETag. **Audit requirements:** template changes/application. **Acceptance criteria:** Given changed template, when existing pinned episode opens, then resolved revision remains unchanged. **Open questions:** template content-vs-config boundary. **Existing implementation evidence:** profile configs and dynamic overrides exist; reusable SaaS template entity absent. **PARTIAL.**

## US-050 — Shared Asset Reuse
**Persona:** producer. **User story:** As a producer, I want to reuse policy-approved assets so that valid work is not regenerated. **Entry conditions:** asset rights/validation permit reuse. **Primary journey:** 1. Find asset. 2. Inspect owner, rights, validation/hash and compatibility. 3. Attach immutable reference. 4. See invalidation effects. **Alternate journeys:** copy-on-write where modification is required. **Failure / recovery journeys:** revoked/shared asset blocks dependent gate without deletion. **API/domain expectations:** ownership, access policy, provenance and reference graph. **Frontend expectations:** reusable/shared labels and compatibility rationale. **Security / tenant-isolation requirements:** no cross-tenant asset exposure absent explicit grant. **Idempotency / concurrency requirements:** attachment key/reference hash. **Audit requirements:** reuse/rights decision. **Acceptance criteria:** Given reusable source imagery, when attached, then new episode references its hash/provenance rather than silently duplicating it. **Open questions:** cross-tenant marketplace policy. **Existing implementation evidence:** reference manifests/artifact repositories/cache concepts exist; SaaS reuse policy/UI absent. **PARTIAL.**

## US-051 — Archive Episode
**Persona:** producer. **User story:** As a producer, I want to archive an episode so that active views stay focused without destructive deletion. **Entry conditions:** archive authorization and nonterminal policy check. **Primary journey:** 1. Select archive. 2. View impact. 3. Confirm. 4. Episode leaves active queues but remains discoverable/auditable. **Alternate journeys:** archive source leaves derivatives readable. **Failure / recovery journeys:** legal/active workflow gate blocks archive. **API/domain expectations:** archival state separate from lifecycle and deletion. **Frontend expectations:** clear inactive status/restore path. **Security / tenant-isolation requirements:** scoped permission. **Idempotency / concurrency requirements:** ETag and idempotent archive. **Audit requirements:** actor/reason/time. **Acceptance criteria:** Given archived episode, when active list loads, then it is omitted unless archive filter selected. **Open questions:** active workflow policy. **Existing implementation evidence:** no archive domain/API found. **MISSING.**

## US-052 — Restore Episode
**Persona:** admin/producer. **User story:** As an authorized user, I want to restore archived content so that legitimate work can continue. **Entry conditions:** archived episode and retention permits. **Primary journey:** 1. Open archive. 2. Inspect reason/age. 3. Restore. 4. Reevaluate current blockers/capabilities. **Alternate journeys:** restore to read-only if policy requires. **Failure / recovery journeys:** purged/retention-expired item explains irrecoverability. **API/domain expectations:** reversible archival transition. **Frontend expectations:** status and new active placement. **Security / tenant-isolation requirements:** restore permission. **Idempotency / concurrency requirements:** ETag/idempotent restore. **Audit requirements:** restore actor/reason. **Acceptance criteria:** Given archived episode, when restored, then prior lineage remains and no workflow is started. **Open questions:** who may restore owner archives. **Existing implementation evidence:** no restore model found. **MISSING.**

## US-053 — Delete Episode / Assets
**Persona:** owner/admin. **User story:** As an owner, I want controlled deletion so that data removal respects sharing, retention and publication consequences. **Entry conditions:** deletion authority/retention evaluation. **Primary journey:** 1. Select resource. 2. See dependent/shared/published implications. 3. Confirm irreversible scope. 4. Execute retention-aware deletion/tombstone. **Alternate journeys:** request deletion when policy requires approval. **Failure / recovery journeys:** shared/published/legal constraint refuses or schedules permitted deletion. **API/domain expectations:** deletion policy/evaluation and tombstone. **Frontend expectations:** explicit impact, typed confirmation, no misleading success. **Security / tenant-isolation requirements:** strongest authorization and step-up where policy dictates. **Idempotency / concurrency requirements:** deletion request key/fence. **Audit requirements:** requester, scope, policy/result. **Acceptance criteria:** Given shared asset, when source episode is deleted, then asset survives until all permitted references are released. **Open questions:** soft-delete/purge windows. **Existing implementation evidence:** no product deletion journey found. **MISSING.**

## US-054 — Retention Policy
**Persona:** owner/admin. **User story:** As an admin, I want to understand tenant retention so that data lifecycle is predictable. **Entry conditions:** policy-read authorization. **Primary journey:** 1. View artifact/workflow/log/approval/source-media categories. 2. See configured duration/holds/export effects. 3. Request permitted change. **Alternate journeys:** inherited platform policy is read-only. **Failure / recovery journeys:** unknown policy blocks destructive action. **API/domain expectations:** policy/version and category application evidence; no invented legal rules. **Frontend expectations:** plain-language effective rules. **Security / tenant-isolation requirements:** retention config restricted. **Idempotency / concurrency requirements:** policy revision. **Audit requirements:** policy/view/change. **Acceptance criteria:** Given no configured retention, when admin views it, then UI declares policy unresolved rather than inventing a period. **Open questions:** actual tenant/platform policy values. **Existing implementation evidence:** retention policy is an explicitly outstanding operational decision in plan/status docs. **MISSING.**

## US-055 — Tenant First-Run
**Persona:** admin. **User story:** As a new tenant admin, I want guided setup so that I can reach a valid first workflow. **Entry conditions:** provisioned tenant/owner identity. **Primary journey:** 1. Establish tenant/session. 2. Inspect capabilities. 3. Create first profile/genre/channel where enabled. 4. Configure voice/profile. 5. Create episode, workflow, review, publish-ready state. **Alternate journeys:** provider-free first-run skips external connection. **Failure / recovery journeys:** unconfigured capability explains next administrator action. **API/domain expectations:** setup readiness aggregate, not a hard-coded wizard state. **Frontend expectations:** mode-aware checklist. **Security / tenant-isolation requirements:** owner setup only. **Idempotency / concurrency requirements:** safe resumable steps. **Audit requirements:** setup changes. **Acceptance criteria:** Given provider-free entitlement, when onboarding completes, then first episode reaches reviewable evidence without external provider. **Open questions:** minimum mandatory setup outside pilot. **Existing implementation evidence:** server-rendered first project/brief journey and provider-free mode; external integrations intentionally disabled. **PARTIAL.**

## US-056 — Provider Connection
**Persona:** admin. **User story:** As an admin, I want safe provider configuration so that server workers can use approved capabilities. **Entry conditions:** provider-configure permission. **Primary journey:** 1. Choose provider/capability. 2. Configure server-side secret reference. 3. See safe configured/identity/health/test status. **Alternate journeys:** retain provider-free mode. **Failure / recovery journeys:** test fails without leaking secret and preserves prior config. **API/domain expectations:** secret reference and provider capability, not browser credential. **Frontend expectations:** status-only secret UI. **Security / tenant-isolation requirements:** KMS/secret boundary. **Idempotency / concurrency requirements:** config ETag/rotation. **Audit requirements:** config/test/rotation. **Acceptance criteria:** Given failed test, when status returns, then diagnostic has no credential value. **Open questions:** supported secret managers. **Existing implementation evidence:** provider-neutral speech architecture, integration-disabled BFF; full SaaS connection flow absent. **PARTIAL.**

## US-057 — YouTube Connection
**Persona:** admin. **User story:** As an admin, I want to authorize a publishing channel so that publication has verified destination authority. **Entry conditions:** channel-management grant. **Primary journey:** 1. ## US-058 — First Successful Episode
**Persona:** producer. **User story:** As a producer, I want the shortest sensible path to a successful episode so that I can prove value. **Entry conditions:** tenant readiness. **Primary journey:** 1. Pick entitled default profile. 2. Enter typed brief. 3. Run provider-free/default workflow. 4. Inspect/decide review. 5. Reach publish-ready evidence. **Alternate journeys:** external publish skipped in pilot. **Failure / recovery journeys:** preflight supplies exact missing configuration. **API/domain expectations:** capability-driven defaults and current gate evaluation. **Frontend expectations:** no optional complexity on critical path. **Security / tenant-isolation requirements:** producer has only needed actions. **Idempotency / concurrency requirements:** pinned episode revision and replay-safe workflow. **Audit requirements:** basic journey events. **Acceptance criteria:** Given a new entitled tenant, when defaults are accepted, then provider-free output reaches current approval state. **Open questions:** canonical demo profile. **Existing implementation evidence:** provider-free project→episode→workflow UI and executor exist; complete publish-ready state varies by profile. **PARTIAL.**
