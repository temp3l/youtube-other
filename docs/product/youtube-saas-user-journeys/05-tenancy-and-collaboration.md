# Tenancy and collaboration

## US-038 — Tenant Membership
**Persona:** admin. **User story:** As an admin, I want to manage tenant membership so that access follows the organization. **Entry conditions:** tenant-admin authorization. **Primary journey:** 1. List members/invitations. 2. Invite/remove/suspend. 3. Assign role. 4. Confirm resulting scope. **Alternate journeys:** identity-provider-managed membership is read-only with a handoff link. **Failure / recovery journeys:** last owner/removal policy blocks unsafe change. **API/domain expectations:** tenant membership is authoritative and separate from API credentials. **Frontend expectations:** displays source of authority and effective role. **Security / tenant-isolation requirements:** admin cannot manage another tenant. **Idempotency / concurrency requirements:** invitation identity and membership ETag. **Audit requirements:** invite/role/remove. **Acceptance criteria:** Given removal, when access is rechecked, then former member cannot read tenant content. **Open questions:** IdP versus local membership authority. **Existing implementation evidence:** BFF session has workspace/principal; Task 08 reports principal multi-workspace discovery remains external. **PARTIAL.**

## US-039 — Roles and Permissions
**Persona:** owner/admin. **User story:** As an owner, I want action-based permissions so that access is least-privilege. **Entry conditions:** tenant policy. **Primary journey:** 1. Inspect owner/admin/producer/reviewer/viewer/service-principal grants. 2. Change permitted role assignment. 3. UI/API evaluate action permission. **Alternate journeys:** custom roles may be unavailable. **Failure / recovery journeys:** denied action explains missing permission without resource disclosure. **API/domain expectations:** action grants include generate/regenerate/approve/publish/configure genre/provider/voice/channel/billing/audit. **Frontend expectations:** controls reflect server decision but server remains authority. **Security / tenant-isolation requirements:** deny by default; service principals scoped. **Idempotency / concurrency requirements:** policy version/ETag. **Audit requirements:** grant changes and sensitive denials. **Acceptance criteria:** Given reviewer role, when publish is attempted, then server denies it despite a stale UI. **Open questions:** custom-role support. **Existing implementation evidence:** `apps/api/src/http-server.ts` maps operation permissions; comprehensive role administration is incomplete. **PARTIAL.**

## US-040 — Audit Trail
**Persona:** admin. **User story:** As an authorized user, I want security-relevant history so that actions are accountable. **Entry conditions:** audit-read grant. **Primary journey:** 1. Filter actor/action/time/resource. 2. Inspect tenant, episode, workflow, revision, hashes, before/after and correlation ID. 3. Link safe resources. **Alternate journeys:** export within retention policy. **Failure / recovery journeys:** redacted/unavailable data states reason. **API/domain expectations:** append-only audit events with typed action/resource bindings. **Frontend expectations:** immutable timeline, not infrastructure logs. **Security / tenant-isolation requirements:** strict tenant filter and role-sensitive fields. **Idempotency / concurrency requirements:** events deduplicated by command/effect identity. **Audit requirements:** this is the audit record. **Acceptance criteria:** Given a review decision, when audit is queried, then actor/hash/revision/time/correlation appear. **Open questions:** actor PII redaction. **Existing implementation evidence:** usage/audit repository/API/BFF view in `packages/persistence/src/postgres-usage-audit-repository.ts`, `apps/api/src/contract.ts`, `apps/web/src/saas-runtime.ts`. **PARTIAL.**
