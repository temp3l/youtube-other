# Localization and media configuration

## US-003 — Speech / Voice Management
**Persona:** admin/producer. **User story:** As an admin, I want server-managed voice profiles so that production uses compatible, consent-valid voices without exposing credentials. **Entry conditions:** profile access.
**Primary journey:** 1. List safe voice profiles by locale/profile. 2. Inspect provider-neutral capability, consent/cloning state, genre default and fallback. 3. Preview through a server action. 4. Assign an authorized default or episode override.
**Alternate journeys:** provider-free voice is shown as disabled/fallback, never simulated as configured. **Failure / recovery journeys:** incompatible/unconsented voice returns typed reason and permitted fallback.
**API/domain expectations:** versioned immutable voice profile, locale compatibility, consent, provider abstraction, preview quota and resolved assignment. **Frontend expectations:** no credential/provider secret, explicit fallback and affected future episodes. **Security / tenant-isolation requirements:** tenant/profile scope; preview does not disclose provider config. **Idempotency / concurrency requirements:** versioned assignments with ETag. **Audit requirements:** default/override/consent-affecting change. **Acceptance criteria:** Given a locale-incompatible voice, when selected, then workflow admission is blocked with a typed reason and fallback state. **Open questions:** consent evidence retention/authority. **Existing implementation evidence:** `apps/api/src/speech-contract.ts`, `apps/api/src/postgres-speech-use-cases.ts`, `apps/web/src/speech-administration.ts`, and ADR-SPEECH-001/002. **PARTIAL.**

## US-004 — Profile Capability Registry
**Persona:** producer. **User story:** As a producer, I want authoritative profile capabilities so that UI choices match admission rules. **Entry conditions:** entitled profile discovery. **Primary journey:** 1. Choose profile. 2. Query capabilities. 3. Select only supported locale/variant/voice/entitlement combination. 4. See typed rejection reason if unavailable.
**Alternate journeys:** configuration changes refresh capabilities before commit. **Failure / recovery journeys:** stale capability response requires refresh/admission recheck.
**API/domain expectations:** typed registry covers locales, variants, voice compatibility, profile availability, entitlements and admission reasons. **Frontend expectations:** consumes returned capabilities, no hard-coded mapping. **Security / tenant-isolation requirements:** profile entitlement filtered per workspace. **Idempotency / concurrency requirements:** capabilities/version returned with admission. **Audit requirements:** admission/rejection only. **Acceptance criteria:** Given an unsupported profile-locale-variant, when chosen, then no run starts and a typed reason appears. **Open questions:** whether to expose capability version publicly. **Existing implementation evidence:** typed profiles/locales/variants in `packages/domain/src/workflow-contracts.ts`, admission validation in `apps/api/src/contract.ts`; web still contains pilot locale maps. **PARTIAL.**

## US-012 — Localization Management
**Persona:** producer. **User story:** As a producer, I want localized derivatives so that one approved source can serve permitted locales. **Entry conditions:** source revision eligible for localization. **Primary journey:** 1. Select source/locale. 2. Inspect reused language-independent assets. 3. Generate/revise translated narration, embedded text, captions, metadata and voice. 4. Validate and track derivative state.
**Alternate journeys:** source-only asset reuse needs no regeneration. **Failure / recovery journeys:** locale-specific failure retains source and marks derivative resumable. **API/domain expectations:** explicit source-to-derivative relation and per-artifact language dependency. **Frontend expectations:** source vs derivative visibility, not a locale filename convention. **Security / tenant-isolation requirements:** source/reuse policy tenant scoped. **Idempotency / concurrency requirements:** source revision and target locale form a unique command key. **Audit requirements:** localization start/reuse/approval. **Acceptance criteria:** Given approved source imagery, when localized to an entitled locale, then it is reused while narration/text are separately versioned. **Open questions:** localized derivative identity/slug policy. **Existing implementation evidence:** `packages/veronica-media/src/localization/translation.ts`, `apps/cli/src/story-localization-commands.ts`, multilingual package code; SaaS derivative management absent. **PARTIAL.**

## US-013 — Locale Admission
**Persona:** producer. **User story:** As a producer, I want a preflight decision so that unsupported genre × locale × voice × render × entitlement work cannot start. **Entry conditions:** intended production selections. **Primary journey:** 1. Submit combination. 2. Receive supported/rejected status and typed reasons. 3. Correct selections or request entitlement. **Alternate journeys:** show fallback only when policy permits. **Failure / recovery journeys:** capability/version race is rechecked at workflow admission.
**API/domain expectations:** deterministic admission evaluator with each constraint and reason. **Frontend expectations:** disable unavailable combinations and retain an explanation. **Security / tenant-isolation requirements:** entitlement evaluation server-side. **Idempotency / concurrency requirements:** same selection/revision receives stable decision within capability version. **Audit requirements:** admitted/rejected workflow request. **Acceptance criteria:** Given missing entitlement, when preflight runs, then no workflow is admitted and entitlement is named. **Open questions:** entitlement grant escalation flow. **Existing implementation evidence:** `workflowAdmissionSchema` and `workflow-admission-composition.ts`; no complete multi-factor UI/API capability registry. **PARTIAL.**

## US-014 — Localization Comparison
**Persona:** producer/reviewer. **User story:** As a reviewer, I want source/localized comparisons so that meaning and locale changes are reviewable. **Entry conditions:** source and derivative exist. **Primary journey:** 1. Select source/target. 2. Compare narration, metadata, language asset substitutions and validation. 3. Record decision against target hashes. **Alternate journeys:** unavailable side is reported. **Failure / recovery journeys:** source change marks comparison stale. **API/domain expectations:** paired lineage and validation projection. **Frontend expectations:** bilingual, media-aware comparison with source/target labels. **Security / tenant-isolation requirements:** both artifacts authorized. **Idempotency / concurrency requirements:** immutable read and target-bound decision. **Audit requirements:** decision references comparison. **Acceptance criteria:** Given different caption validation, when compared, then locale-specific failure is visible separately. **Open questions:** human translation-quality rubric. **Existing implementation evidence:** translation and artifacts exist; paired comparison absent. **MISSING.**

## US-015 — Bulk Localization
**Persona:** producer. **User story:** As a producer, I want bulk localization so that approved sources can be expanded safely. **Entry conditions:** selected sources and target locales. **Primary journey:** 1. Preflight each tuple. 2. Confirm eligible rows. 3. Start batch. 4. Monitor progress/results. 5. Retry safe failed items. **Alternate journeys:** remove failed/ineligible items. **Failure / recovery journeys:** partial failure is per-item, never hides completed derivatives. **API/domain expectations:** batch command, child run IDs, aggregate/preflight results. **Frontend expectations:** matrix with per-item reason/controls. **Security / tenant-isolation requirements:** every source/locale is reauthorized. **Idempotency / concurrency requirements:** batch and tuple keys. **Audit requirements:** selection, preflight, per-item results. **Acceptance criteria:** Given mixed locale support, when launched, then only eligible rows run and rejected rows preserve typed reasons. **Open questions:** concurrency limits. **Existing implementation evidence:** multilingual single-workflow artifacts exist; SaaS batch localization absent. **MISSING.**

## US-016 — Genre Configuration
**Persona:** admin/producer. **User story:** As an admin, I want genre defaults so that production has consistent policy. **Entry conditions:** `genre.configure` authorization. **Primary journey:** 1. Inspect profile defaults. 2. Edit permitted storytelling, narration, visual/image/camera/reference, TTS, localization, map/diagram, review and render policies. 3. Validate/publish configuration version. **Alternate journeys:** draft versus active version. **Failure / recovery journeys:** invalid combination identifies field and preserves active version. **API/domain expectations:** versioned profile/policy resource, not episode content. **Frontend expectations:** group policy with inheritance markers. **Security / tenant-isolation requirements:** privileged, tenant/platform boundary. **Idempotency / concurrency requirements:** strong version precondition. **Audit requirements:** before/after configuration and version. **Acceptance criteria:** Given a changed genre TTS default, when saved, then only future resolution changes. **Open questions:** platform-managed versus tenant-editable fields. **Existing implementation evidence:** content-profile policy contracts and Strategic configuration files exist; generic admin UI/config API is incomplete. **PARTIAL.**

## US-017 — Configuration Inheritance
**Persona:** admin/producer. **User story:** As a producer, I want resolved configuration and provenance so that I know what an episode will use. **Entry conditions:** profile/tenant configuration and episode revision. **Primary journey:** 1. Inspect platform → tenant/channel → genre → episode override → resolved revision values. 2. Edit only permitted layer. 3. Pin resolved configuration for workflow. **Alternate journeys:** reset an override to inherited. **Failure / recovery journeys:** removed/invalid ancestor blocks resolution. **API/domain expectations:** resolved immutable configuration snapshot with source at each field. **Frontend expectations:** inherited/override distinction; no hidden defaults. **Security / tenant-isolation requirements:** no platform policy leakage. **Idempotency / concurrency requirements:** configuration revision pinned during workflow. **Audit requirements:** layer/field change and resolution. **Acceptance criteria:** Given episode override, when a workflow starts, then its revision retains the resolved value after later default changes. **Open questions:** channel layer applicability outside YouTube. **Existing implementation evidence:** profile policy contracts and dynamic overrides exist; universal precedence/resolved UI absent. **PARTIAL.**

## US-018 — Visual Profile Management
**Persona:** producer. **User story:** As a producer, I want to inspect and control an episode visual profile so that image generation is coherent and repeatable. **Entry conditions:** visual-capable profile. **Primary journey:** 1. Open derived/cached profile. 2. See model/version/time/lock state. 3. Reuse, deliberately regenerate, or create allowed override. 4. Confirm affected units. **Alternate journeys:** approved profile stays locked. **Failure / recovery journeys:** stale profile directs regeneration/review. **API/domain expectations:** explicit profile artifact/cache lineage and lock. **Frontend expectations:** declaration of reuse vs regeneration. **Security / tenant-isolation requirements:** provider/model details sanitized. **Idempotency / concurrency requirements:** input fingerprint/cache key and ETag. **Audit requirements:** generate/lock/override. **Acceptance criteria:** Given approved profile, when an image is regenerated, then profile reuse is shown and no hidden profile changes occur. **Open questions:** user-editable fields. **Existing implementation evidence:** image pipeline/visual contracts and planner exist (`packages/image-generation`, `packages/veronica-media/src/planning`); SaaS management surface absent. **PARTIAL.**

## US-019 — Voice Assignment
**Persona:** producer/admin. **User story:** As a user, I want voice assignment controls so that locale-ready, consent-valid choices are intentional. **Entry conditions:** available voice capability. **Primary journey:** 1. Preview eligible voices. 2. Set genre default or episode override. 3. View consent/locales/fallback and future impact. **Alternate journeys:** keep inherited default. **Failure / recovery journeys:** revoked consent invalidates admission and prompts replacement. **API/domain expectations:** assignment resolves against versioned voice profile and locale. **Frontend expectations:** preview/status no secrets; scope-of-impact preview. **Security / tenant-isolation requirements:** consent records remain server-side. **Idempotency / concurrency requirements:** idempotent assignment and revision pin. **Audit requirements:** actor/scope/old/new voice profile. **Acceptance criteria:** Given a genre default change, when confirmed, then existing pinned revisions stay unchanged and affected future episodes are listed. **Open questions:** cloned-voice approval workflow. **Existing implementation evidence:** speech contracts/ADR and BFF settings status exist; assignment/preview operation is not product-complete. **PARTIAL.**
