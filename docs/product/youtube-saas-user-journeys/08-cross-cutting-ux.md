# Cross-cutting UX

## US-059 — Global Search / Navigation
**Persona:** all users. **User story:** As a user, I want to locate production objects by recognizable information so that I do not need internal IDs. **Entry conditions:** authenticated session. **Primary journey:** 1. Open global search/navigation. 2. Enter title/name/channel/locale/status. 3. See authorized episodes, workflows, reviews, artifacts, publications. 4. Navigate to safe detail. **Alternate journeys:** direct contextual navigation from queue/audit. **Failure / recovery journeys:** no results offers filter guidance; forbidden resources never reveal existence. **API/domain expectations:** tenant-scoped typed search index/read model. **Frontend expectations:** labels/internal IDs secondary. **Security / tenant-isolation requirements:** authorization before ranking/snippets. **Idempotency / concurrency requirements:** read-only/eventually consistent label. **Audit requirements:** sensitive search audit if policy requires. **Acceptance criteria:** Given known episode title, when producer searches, then authorized episode appears without knowing its ID. **Open questions:** indexing/retention of artifact text. **Existing implementation evidence:** sidebar navigation exists in `apps/web/src/saas-runtime.ts`; global search absent. **PARTIAL.**

## US-060 — Notifications / Action Center
**Persona:** all users. **User story:** As a user, I want actionable in-product events so that I know what needs attention. **Entry conditions:** user with relevant work. **Primary journey:** 1. Open action center. 2. See workflow attention, review assignment/completion, failure, publish-ready/failure. 3. Open actionable context. 4. Mark read/dismiss according to policy. **Alternate journeys:** no email/push is assumed. **Failure / recovery journeys:** expired action becomes historical with reason. **API/domain expectations:** tenant/user-targeted notification projection from domain events, distinct from webhooks. **Frontend expectations:** priority/currentness and deep links. **Security / tenant-isolation requirements:** recipient authorization rechecked on open. **Idempotency / concurrency requirements:** event/action dedupe. **Audit requirements:** action state changes where material. **Acceptance criteria:** Given workflow failure, when producer opens action center, then it sees one safe actionable notification linked to run. **Open questions:** assignment and notification retention. **Existing implementation evidence:** workflow/review events exist; product action center absent. **MISSING.**

## US-061 — Safe Destructive Actions
**Persona:** all users. **User story:** As a user, I want impact-aware confirmations so that regenerate, retry, cancel, delete, revoke and republish are intentional. **Entry conditions:** action is authorized and eligible. **Primary journey:** 1. Select action. 2. Display affected artifacts/cost/invalidations/publication consequences. 3. Require meaningful confirmation. 4. Submit preconditioned command and show result. **Alternate journeys:** irreversible action requires elevated confirmation. **Failure / recovery journeys:** changed state during confirm yields conflict/refresh, not hidden execution. **API/domain expectations:** each command has impact/elegibility evaluation. **Frontend expectations:** distinguish reversible, destructive and irrecoverable. **Security / tenant-isolation requirements:** server reauthorization/step-up as policy dictates. **Idempotency / concurrency requirements:** keys/ETags/fences. **Audit requirements:** confirmation/action/correlation. **Acceptance criteria:** Given cancel would abandon running steps, when confirmed on stale run version, then no cancellation occurs and current state is shown. **Open questions:** republish policy. **Existing implementation evidence:** cancel/resume and revoke require preconditions; safe impact previews are incomplete. **PARTIAL.**

## US-062 — Optimistic Concurrency / Stale UI
**Persona:** all users. **User story:** As a user, I want clear stale-state handling so that concurrent edits/reviews cannot overwrite or misapprove work. **Entry conditions:** mutable versioned resource. **Primary journey:** 1. Open resource with version/ETag. 2. Another actor changes it. 3. Submit. 4. Receive conflict with current version and safe comparison/reload. 5. Reapply intentionally. **Alternate journeys:** immutable challenge is consumed by another reviewer. **Failure / recovery journeys:** retry only after re-read; no blind overwrite. **API/domain expectations:** strong ETags for mutations, immutable hash/revision binding for approvals, typed conflict. **Frontend expectations:** preserve draft where safe and identify changed fields. **Security / tenant-isolation requirements:** conflict response avoids hidden-resource disclosure. **Idempotency / concurrency requirements:** all listed high-impact commands preconditioned. **Audit requirements:** conflict resolution action where material. **Acceptance criteria:** Given two producers edit same brief, when second saves old revision, then API returns conflict and UI does not overwrite first change. **Open questions:** merge support for structured briefs. **Existing implementation evidence:** web reports 412 feedback and API uses `If-Match`; approval challenges are consumed/expiry-bound. **PARTIAL.**
